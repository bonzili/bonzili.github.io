# CISSP sync Worker

A small Cloudflare Worker + D1 service for the CISSP Field Manual's optional
cross-device sync. It stores one opaque, client-encrypted snapshot per device.
It receives the sync code only to derive an account id, never stores it, and never sees plaintext progress.

## What it stores

```
progress(
  account   TEXT,  -- SHA-256("cissp-sync-account:" + sync code)
  device    TEXT,  -- random device id generated by the browser
  envelope  TEXT,  -- client-encrypted JSON {v, iv, ct}
  updated_at INTEGER,
  PRIMARY KEY(account, device)
)
```

Each device writes only its own row. The browser merges the decrypted rows.

## Deploy

You need Node.js 20+ and a Cloudflare account with `bonzili.me` active.

```bash
cd sync-worker
npx wrangler login
npx wrangler d1 create cissp-sync
```

Copy the returned `database_id` into `wrangler.toml`, replacing
`REPLACE_WITH_YOUR_D1_DATABASE_ID`.

```bash
npx wrangler d1 execute cissp-sync --remote --file=./schema.sql
npx wrangler deploy
```

Then add the custom domain:

1. Cloudflare dashboard → **Workers & Pages** → `cissp-sync`.
2. **Settings → Domains & Routes → Add custom domain**.
3. Enter `sync.bonzili.me`.

The zone's Universal SSL certificate already covers `*.bonzili.me`, so no extra
certificate is needed.

## Rate limiting

In Cloudflare: **Security → WAF → Rate limiting rules**. The Free plan includes
one rule.

Protect the **whole `sync.bonzili.me` host**, not only `/v1/sync`: unknown paths
and `/v1/health` also invoke the Worker and count against the Workers request
allowance.

- If the dashboard offers **All incoming requests**, use that.
- Otherwise use `starts_with(http.request.uri.path, "/")`.
- 30 requests per 10 seconds per IP
- Block for 10 seconds

Only `sync.bonzili.me` is proxied in this setup, so the rule does not affect the
DNS-only `bonzili.me` site. If you later proxy the main site, scope the rule to
the sync host or use a WAF custom rule; the Free plan's rate-limiting fields do
not include the host.

The sync client debounces to one request every few seconds, so normal use stays
well below this.

## Lock to one account (optional, recommended)

By default the Worker accepts any well-formed 128-bit sync code. An anonymous
request with a random code gets an empty account; a POST can create a junk row.
The sync code is unguessable, so this is not a data-access risk, but it can
consume D1 writes.

After creating your sync code in the app:

1. Open **Progress → Sync across devices → Server lock (advanced)**.
2. Click **Show lock value** and copy the 64-character fingerprint.
3. Set it in `wrangler.toml`:

   ```toml
   [vars]
   ACCOUNT_ID = "your-64-character-fingerprint"
   ```

   Or set `ACCOUNT_ID` under **Workers & Pages → cissp-sync → Settings →
   Variables** in the dashboard.
4. Redeploy with `npx wrangler deploy`.

The Worker now returns `401` for every other account before it reads or writes
D1. The fingerprint is `SHA-256("cissp-sync-account:" + code)`. It is not the
sync code and cannot decrypt progress. It does **not** stop request floods;
the `/v1/sync` rate-limit rule is the control for that.

If you later create a new sync code, update `ACCOUNT_ID` to the new
fingerprint. The old account is no longer accepted.

## Local development

```bash
cd sync-worker
npx wrangler dev
```

The Worker runs at `http://127.0.0.1:8787`. The Worker's CORS allowlist includes
`http://localhost:8000` and `http://127.0.0.1:8000`.

To point the app at the local Worker, set the override before the app loads:

```html
<script>window.CISSP_SYNC_API_URL = "http://127.0.0.1:8787/v1/sync";</script>
```

Or set it in the browser console before clicking **Sync now**. `sync.js` reads
the global when it makes a request.

For a temporary `workers.dev` deployment, use:

```js
window.CISSP_SYNC_API_URL = "https://cissp-sync.<account>.workers.dev/v1/sync";
```

## API

All requests need `Authorization: Bearer <32-hex sync code>`.

| Method | Path | Body | Result |
| --- | --- | --- | --- |
| `GET` | `/v1/sync` | — | all device envelopes |
| `POST` | `/v1/sync` | `{deviceId, envelope}` | upsert this device, return all |
| `DELETE` | `/v1/sync` | `{deviceId}` or `{all:true}` | remove one/all device rows |
| `GET` | `/v1/health` | — | `{ok:true}` |

The account id is `SHA-256("cissp-sync-account:" + code)`. The code itself is
never written to D1.

## Limits and failure modes

- 10 devices per sync code.
- 900 KB request cap. The app's state is normally well under 200 KB.
- D1 free plan: 5 million rows read/day, 100,000 rows written/day, 5 GB.
  Two devices syncing a few hundred times a day is a tiny fraction of this.
- The Free plan fails requests when daily limits are exceeded; it does not
  automatically bill overages.
- If the Worker is down or offline, the app keeps working locally and retries
  on the next save, visibility change, or **Sync now**.

## Security notes

- The browser derives an AES-GCM-256 key from the sync code with HKDF-SHA-256.
  The Worker only stores ciphertext.
- The sync code is the only key. Losing it means losing access to the server
  copy; local progress remains.
- Anyone with the code can read and change the synced progress. Treat it like a
  passphrase.
- The code travels in the `Authorization` header over HTTPS; do not put it in a
  URL, analytics event, or log.
- The Worker does not log request bodies. Cloudflare may still process standard
  request metadata (IP, time, status) as part of normal operation.
- Deleting the account removes the stored rows, but another device that still
  has the code and its local progress can upload it again. Turn sync off on the
  other devices before deleting the account if you want a complete removal.

## Bot Fight Mode

If you enable Cloudflare Bot Fight Mode on the zone, test the sync endpoint from
both devices. On the Free plan, Bot Fight Mode cannot be bypassed with WAF skip
rules, and it may challenge the browser `fetch()` calls used by sync. The 128-bit
sync code, end-to-end encryption, and the `/v1/sync` rate-limit rule already
cover the API; Bot Fight Mode is optional.
